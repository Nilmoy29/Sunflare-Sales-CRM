## What Went Well

**Alice (Product Owner):** Epic 4 delivers the full sales pipeline managers asked for — board, filters, 360 detail, notes, follow-ups, audit, push, and governance (lost reasons + reassignment). D2D and call-sourced leads share one funnel.

**Charlie (Senior Dev):** Story sequencing was excellent. Schema and RLS (4.1) before Kanban (4.2) before enrichment (4.3) prevented rework. Explicit deferrals in early stories (`lost_reason` → 4.9, push → 4.8, audit → 4.7) kept each story reviewable.

**Amelia (Developer):** The pipeline module became a coherent vertical slice:
- `src/features/pipeline/*` — server reads/writes, enrichment, hooks
- `src/components/pipeline/*` — Kanban, filters, detail, compose UIs
- `PATCH /api/v1/leads/:id/stage` extended incrementally (4.2 → 4.7 → 4.9)
- `fetch` + `usePipelineLeads` / `useLeadDetail` — no TanStack Query, consistent with Epic 3

**Dana (QA):** `@dnd-kit` Kanban with lost-reason modal gating (4.9) is the right UX for data quality. Code reviews caught real client bugs: unhandled drag rejections (4.2), filter/stage mismatch after drag (4.3), dialog closing on failed PATCH (4.9).

**Winston (Architect):** RLS model held: rep-owned leads, admin sees all. Reassignment (4.9) correctly uses admin-only API + existing `leads_update_admin`. Stage audit JSON extension (4.7 → 4.9 `lost_reason`) avoided schema churn on `lead_activity`.

## Challenges and Growth Areas

**Charlie (Senior Dev):** `moveLeadStage` optimistic updates caused repeated review findings across 4.2, 4.3, and 4.9. The hook swallows errors (by design for board error banner) but callers like the lost-reason dialog need return values — we fixed 4.9 but the pattern should be documented.

**Elena (Junior Dev):** Multi-step flows (drag → modal → PATCH) are harder to reason about than single API calls. Lost-reason gating required careful ordering: no optimistic move until confirm.

**Alice (Product Owner):** Lead detail still shows `calls_available: false` — correct per 4.4, but stakeholders demoing "360 view" will notice the calls gap until Epic 5.

**Dana (QA):** Web push (4.8) has platform caveats (iOS PWA, 5-min cron lag, no retroactive push after `reminded_at` skip). Manual QA matrix is large; no Playwright for pipeline drag or push.

**Winston (Architect):** Non-atomic multi-write operations appeared in 4.7 (stage + audit) and 4.9 (lead + follow_ups). Acceptable v1, but Epic 5+ should use RPC transactions when business rules require paired updates.

## Key Lessons Learned

1. **Defer scope in story specs, deliver in named later stories.** `lost_reason` enum in 4.1, column in 4.9; push in 4.8 after follow-ups in 4.6 — zero mid-epic scope creep.

2. **Extend one PATCH endpoint instead of proliferating routes.** Stage changes, audit side effects, and lost reasons all hang off `PATCH .../stage` — easier to secure and test.

3. **Modal gates must not trust fire-and-forget hooks.** Any hook that catches errors internally needs a success signal for multi-step UI (lost-reason dialog pattern).

4. **Enrichment layer is the pipeline's secret weapon.** `enrichPipelineLeads` centralizes `last_touch_at` and countdown — new features (notes, stage audit, follow-ups) plug in without card schema churn.

5. **Code review density correlates with client interaction complexity.** Kanban + hooks + push had the most patches; schema stories (4.1) had fewer runtime bugs but critical RLS fixes.
